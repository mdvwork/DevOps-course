# K3-01 — CI/CD и стратегия веток

## 1. Цель

Описать процесс проверки изменений, тестирования приложения, сборки Docker-образа и принятия решения о выпуске.

## 2. Различия между CI, Continuous Delivery и Continuous Deployment

- **Continuous Integration (CI)** — регулярное объединение изменений в общей кодовой базе с автоматическими проверками. В этом проекте CI будет запускаться при `push` и `pull_request`, проверять код автоматическими тестами и показывать результат в GitHub Actions.
- **Continuous Delivery** — после успешных проверок приложение и артефакты подготовлены к выпуску, но решение о выпуске в production остаётся за человеком или отдельным процессом подтверждения.
- **Continuous Deployment** — каждое изменение, успешно прошедшее все необходимые автоматические проверки, автоматически разворачивается в production без ручного подтверждения.

## 3. Схема веток и проверок

    feature/fix branch
           |
           | push
           v
    GitHub Actions
    - подготовка Python
    - автоматические тесты
    - сборка Docker-образа после тестов
           |
           v
      Pull Request
           |
           | проверки успешны, изменения рассмотрены
           v
          main
           |
           v
    Решение о выпуске / подготовка к выпуску

В рамках учебной работы изменения выполняются в отдельной ветке `kt3`. Workflow должен запускаться на событиях `push` и `pull_request`. Сборка Docker-образа должна зависеть от успешного завершения тестов.

## 4. Что проверяется в проекте

В `tests/test_app.py` находятся интеграционные тесты приложения Web/API. Они проверяют создание запросов, повторную отправку без дублирования, обработку некорректного запроса, восстановление API после сбоя, метрики, баннер и ответ для неизвестного пути.

В предоставленном шаблоне `templates/student-ci.yml.example` уже настроены события `push` и `pull_request`, runner `ubuntu-latest`, checkout исходного кода и Python 3.13. На начальном этапе команда `python --version` подтверждает настройку Python, но не проверяет работоспособность приложения. Запуск тестов и сборка образа будут добавлены в следующих заданиях K3-03 и K3-04.

## 5. Сравнение с Git-flow

Git-flow использует несколько долгоживущих веток и дополнительные типы веток, например `develop`, `release/*` и `hotfix/*`. Он может быть полезен в командах со сложным процессом выпуска и поддержкой нескольких версий.

Для короткой учебной работы достаточно простой схемы: отдельная рабочая ветка, Pull Request, автоматические проверки и `main`. Она уменьшает число веток и упрощает понимание того, какие проверки должны пройти до объединения изменений.

## 6. Критерии принятия решения о выпуске

1. Автоматические тесты завершились успешно.
2. Docker-образ успешно собран после тестов.
3. Pull Request проверен, а изменения готовы к объединению в `main`.
4. Сам факт успешной сборки не считается подтверждением развёртывания приложения.

## 7. Проверка понимания

**Является ли сборка образа автоматическим deployment?**

Нет. Сборка Docker-образа создаёт артефакт, который можно использовать для запуска приложения. Deployment означает развёртывание этого артефакта в целевой среде. Чтобы считать процесс автоматическим deployment, нужно отдельно настроить и выполнить этап развёртывания.

Команды, использованные для проверки исходного состояния проекта:

    git branch --show-current
    git log --oneline -3
    git status
    cat templates/student-ci.yml.example
    ls -la tests
    sed -n '1,240p' tests/test_app.py

Наблюдения:
- Текущая рабочая ветка — `kt3`.
- Предыдущие задания K2-01 — K2-05 присутствуют в истории текущей ветки.
- Шаблон Student CI запускается на событиях `push` и `pull_request`.
- В шаблоне используется Python 3.13 на runner `ubuntu-latest`.
- Автоматические тесты находятся в `tests/test_app.py`.
- На момент подготовки этого отчёта запуск тестов и сборка Docker-образа ещё не добавлены в workflow.

## 9. Вывод

Для проекта выбрана простая схема ветка → Pull Request → main с автоматическими проверками. Она подходит для учебной работы, поскольку позволяет отдельно проверить изменения до их объединения. Следующие этапы добавят реальный запуск тестов и сборку Docker-образа, зависящую от успешных тестов.
