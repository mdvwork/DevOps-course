
# K4-01. Логи и доступность

## 1. Запуск приложения

Команды:

```bash
docker compose -f compose.student.yaml config
docker compose -f compose.student.yaml up -d
docker compose -f compose.student.yaml ps
```

Результат:
- Конфигурация Compose успешно проверена.
- Контейнер api получил статус healthy.
- Контейнер web после запуска также получил статус healthy.
- Web доступен через 127.0.0.1:8080.
- Оба сервиса используют образ devops-student:v1.

## 2. Успешный пользовательский сценарий

Открыт адрес http://localhost:8080.
Создана заявка №12.

Тип заявки: screen (не работает экран).
Интерфейс подтвердил принятие заявки.

## 3. Логи API

Команда:

```bash
docker compose -f compose.student.yaml logs --tail=30 api
```

Наблюдения:
- В 16:55:38.563 UTC API записал событие request_accepted с request_id=12.
- В 16:55:38.563 UTC API обработал POST /api/requests с HTTP 201.
- В 16:55:38.568 UTC API обработал GET /api/requests с HTTP 200.
- Регулярно выполнялись GET /health с HTTP 200.

## 4. Логи Web

Команда:

```bash
docker compose -f compose.student.yaml logs --tail=30 web
```

Наблюдения:
- В 16:55:38.563 UTC Web обработал POST /api/requests с HTTP 201.
- В 16:55:38.568 UTC Web обработал GET /api/requests с HTTP 200.
- Регулярно выполнялись GET /health с HTTP 200.

## 5. Связь времени и действия

Создание заявки №12 в браузере соответствует событию request_accepted в API и успешному POST в логах Web.

Время API и Web практически совпадает:
- API: 16:55:38.563 UTC.
- Web: 16:55:38.563 UTC.

Это подтверждает прохождение запроса через Web к API и успешное создание заявки.

## 6. Проверка адресов

Команда:

```bash
curl -i http://localhost:8080/health
```

Ответ: HTTP 200 OK.

```json
{"process": "running", "role": "web"}
```

Команда:

```bash
curl -i http://localhost:8080/api/requests
```

Ответ: HTTP 200 OK.

В ответе:
- total: 10;
- присутствует заявка №12;
- возвращается список ранее созданных заявок.

## 7. Различие проверок

/health проверяет, что процесс Web работает и отвечает.
Эта проверка сама по себе не подтверждает доступность API.

GET /api/requests проверяет функциональный путь получения заявок через Web и API.

Healthcheck API отдельно проверяет доступность самого API.

Для обнаружения отказа зависимости нужна readiness-проверка Web, которая дополнительно проверяет доступность API.

Проверка понимания:
Отказ зависимости обнаружит проверка готовности Web, если она включает обращение к API. Текущий /health Web проверяет только собственный процесс.

## 8. Вывод

Приложение успешно запущено с помощью compose.student.yaml.
Оба контейнера получили статус healthy.
Заявка №12 успешно создана и присутствует в списке.
Логи Web и API подтверждают обработку POST с HTTP 201 и последующее получение списка с HTTP 200.
Проверки /health и /api/requests подтвердили различие между доступностью процесса и работоспособностью функционального пути приложения.
