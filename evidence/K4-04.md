# K4-04 — Инцидент: отказ API и восстановление

## 1. Исходное состояние

Перед началом проверки API и Web работали.

Запрос:

    curl -i http://localhost:8080/api/requests

Результат:
- HTTP 200 OK.
- Всего сохранено 11 заявок.
- Последняя заявка: id 13.
- Web успешно получал данные от API.

## 2. Воспроизведение инцидента

Остановил API:

    docker compose -f compose.student.yaml stop api

После остановки API повторил запрос:

    curl -i http://localhost:8080/api/requests

Результат:
- HTTP 503 Service Unavailable.
- Ответ: upstream_unavailable.
- Web не смог получить данные от API.

## 3. Обнаружение причины

Проверил журналы Web:

    docker compose -f compose.student.yaml logs --since 2m web

В журнале обнаружено событие upstream_unavailable.

В сообщении об ошибке присутствовало:

    No address associated with hostname

Целевой адрес API: http://api:8000.

Причина инцидента: контейнер API был остановлен, поэтому Web не мог обратиться к нему через внутреннее DNS-имя Docker Compose api.

## 4. Проверка мониторинга

В Prometheus выполнил запрос:

    up{job="workshop"}

Во время инцидента:
- api:8000 — 0.
- web:8000 — 1.

Проверил количество ошибок HTTP 503:

    devops_http_requests_total{role="web",status="503"}

Результат: значение 1.

Это подтвердило, что Web продолжал работать, но не мог получить данные от API.

## 5. Восстановление API

Запустил ранее остановленный контейнер:

    docker compose -f compose.student.yaml start api

Проверил состояние сервисов:

    docker compose -f compose.student.yaml ps

Результат:
- API — Up (healthy).
- Web — Up (healthy).
- Prometheus и Grafana продолжили работать.

Повторно проверил Prometheus:

    up{job="workshop"}

Оба target вернули значение 1:
- api:8000 — 1.
- web:8000 — 1.

## 6. Проверка после восстановления

Повторил запрос:

    curl -i http://localhost:8080/api/requests

Результат:
- HTTP 200 OK.
- Все 11 прежних заявок сохранились.
- Последняя прежняя запись по-прежнему имела id 13.

Затем через веб-интерфейс создал новые заявки.

Повторная проверка:

    curl -s http://localhost:8080/api/requests

Результат:
- Всего 14 заявок.
- Новые записи получили id 14, 15 и 16.
- Новые заявки успешно сохранились и отображаются через API.

## 7. Хронология инцидента

1. API был остановлен вручную.
2. Web продолжил работать, но запросы к API завершались HTTP 503.
3. Логи Web показали upstream_unavailable.
4. Prometheus обнаружил недоступность API: up = 0.
5. API был запущен повторно командой docker compose start api.
6. API прошёл healthcheck, оба target Prometheus вернулись к up = 1.
7. Web снова стал возвращать HTTP 200.
8. Проверка подтвердила сохранность старых данных и создание новых заявок.

## 8. Выводы и восстановление

Это был отказ отдельного сервиса-зависимости, а не ошибка новой версии приложения.

В данном случае откат (rollback) образа не требовался: версия приложения не менялась. Для восстановления достаточно было перезапустить остановленный контейнер API.

При инциденте после неудачного обновления приложения мог бы потребоваться rollback к предыдущей проверенной версии образа.

Проверка показала:
- мониторинг позволяет обнаружить недоступность API;
- Web сохраняет работоспособность, но возвращает понятную ошибку при недоступности зависимости;
- Docker volume сохраняет заявки при остановке API;
- после восстановления API приложение снова обрабатывает запросы и принимает новые данные.

**Итог:** инцидент воспроизведён, диагностирован и устранён. Работоспособность системы после восстановления подтверждена.
