# K4-03. Ansible и управление конфигурацией

## 1. Подготовка Ansible

Для выполнения playbook был собран Docker-образ:

`docker build -f docker/ansible.Dockerfile -t devops-course-ansible:base .`

В образ установлена версия Ansible Core 2.19.14.

Сервис Ansible в Docker Compose использует этот образ. Каталог `ansible` монтируется в `/work`, а общая Docker volume `requests` — в `/data`.

## 2. Проверка demo.yml

Первый запуск:

`docker compose run --rm ansible demo.yml`

Результат:
- ok=1
- changed=1
- failed=0

При первом запуске создан файл `/data/demo.txt`.

Повторный запуск дал:
- ok=1
- changed=0
- failed=0

Это подтверждает идемпотентность playbook: повторное применение конфигурации не изменяет файл, если его состояние уже соответствует заданному.

## 3. Создание banner.yml

На основе `ansible/banner.yml.example` создан файл `ansible/banner.yml`.

В переменной `workshop_message` задано сообщение:

`Group: AAA | Student: student-A`

Playbook использует модуль `ansible.builtin.copy` для управления файлом `/data/banner.txt`.

Параметры файла:
- content — значение переменной `workshop_message`;
- mode — 0644;
- owner — 10001;
- group — 10001.

## 4. Проверка banner.yml

Первый запуск:

`docker compose run --rm ansible banner.yml`

Результат:
- ok=1
- changed=1
- failed=0

Повторный запуск:
- ok=1
- changed=0
- failed=0

Таким образом, подтверждена идемпотентность настройки баннера.

## 5. Проверка API и обновление конфигурации

Первоначальная проверка:

`curl -i http://localhost:8080/api/banner`

Получен ответ HTTP 200 OK:

`{"message": "Group: AAA | Student: student-A"}`

Затем переменная `workshop_message` была изменена на:

`Group: AAA | Student: student-A | Banner version: 2`

После повторного запуска playbook результат:
- ok=1
- changed=1
- failed=0

Повторная проверка API вернула HTTP 200 OK и обновлённое сообщение:

`{"message": "Group: AAA | Student: student-A | Banner version: 2"}`

## 6. Почему SSH не используется

В этом задании Ansible работает локально внутри Docker-контейнера.

В playbook указаны:
- hosts: localhost;
- connection: local.

Поэтому Ansible выполняет задачи на локальном узле без SSH-подключения.

Для управления удалённым Linux-сервером потребовались бы:
- адрес сервера и пользователь в inventory;
- SSH-доступ и настроенная аутентификация;
- сетевое соединение с сервером;
- SSH-клиент в Ansible-контейнере;
- Python на удалённом сервере;
- при необходимости повышение привилегий через become.

## 7. Вывод

Ansible успешно запущен в Docker-контейнере.

Проверены два playbook: `demo.yml` и `banner.yml`. Повторное применение конфигурации не вызывает изменений, если целевое состояние уже достигнуто.

Также проверено обновление баннера при изменении переменной и подтверждена передача нового содержимого через API.

Практика продемонстрировала декларативное управление конфигурацией и принцип идемпотентности Ansible.
