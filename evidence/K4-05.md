## 5. Архитектура, сеть и данные

Сервисы `api` и `web` используют один образ приложения, но разные переменные окружения.

Web обращается к API по адресу `http://api:8000`. Имя `api` разрешается через внутреннюю сеть Docker Compose.

API сохраняет заявки в `/data`, который подключён к именованному volume `requests`. Это позволяет сохранять данные при перезапуске контейнера.

Приложение работает от непривилегированного пользователя `10001:10001`.

## 6. Мониторинг и восстановление

Prometheus собирает метрики API и Web. Проверка `up{job="workshop"}` показывала обе цели со значением 1 после восстановления.

Во время K4-04 была остановлена служба API. Web возвращал HTTP 503 с ошибкой `upstream_unavailable`. В Prometheus значение API было 0, Web — 1. Счётчик запросов Web со статусом 503 увеличился.

После команды `docker compose -f compose.student.yaml start api` API снова стал healthy, обе цели Prometheus вернулись к значению 1, а запрос к `/api/requests` снова вернул HTTP 200. Ранее сохранённые заявки остались доступны.

## 7. Ansible и индивидуальное изменение

В рамках K4-05 изменён параметр `workshop_message` в `ansible/banner.yml`.

Новое значение:

`Group: AAA | Student: student-A | Banner version: 3 | K4-05 defense`

Команда применения:

`docker compose -f compose.student.yaml --profile tools run --rm ansible banner.yml`

Результат Ansible: `ok=1 changed=1 unreachable=0 failed=0`.

Проверка: `curl -i http://localhost:8080/api/banner`.

API вернул HTTP 200 и JSON с новым сообщением. Это подтвердило путь от Ansible playbook через общий volume к API.

## 8. CI

В репозитории настроены две активные workflow:
- `.github/workflows/student-ci.yml`;
- `.github/workflows/course-check.yml`.

Student CI запускает тесты на Python 3.13 и собирает образ с тегом Git SHA. Course checks проверяет конфигурацию Compose, тесты и контейнерные сценарии.

На момент подготовки этого отчёта `gh run list --branch kt4 --limit 10` вернул `no runs found`. Ветка `kt4` ещё не была опубликована в `origin`, поэтому успешные удалённые запуски CI для неё не заявляются.

Локальные тесты и сборка образа проверены отдельно; это не заменяет проверку GitHub Actions.

## 9. Проверка перед выпуском

Следующая необходимая проверка перед настоящим выпуском — сквозное тестирование кандидата на релиз в staging-среде, близкой к production. Нужно проверить взаимодействие сервисов, восстановление данных из резервной копии, безопасность конфигурации, поведение под нагрузкой и возможность отката версии.

Выполнена локальная проверка тестов, сборки Docker-образа и запуска контейнера. Проверены сетевое взаимодействие Web и API, сохранение данных в volume, мониторинг, восстановление после недоступности API и применение индивидуального изменения через Ansible.
