# K3-03. Тестовый барьер

Шаг тестов стоит сразу после печати версии Python и запускает только `tests/test_app.py`:

```yaml
- name: Run application tests
  run: python -m unittest discover -s tests -p test_app.py -v
```

Код выхода команды не скрывается.

## Что именно обязано быть истинным

Контракт `test_create_request`: новый запрос экрана (`kind=screen`, ключ `test-create`) создаётся один раз и возвращает HTTP `201`. Затем GET списка показывает `total == 1`. Статус `201` в тесте — ожидаемое значение, его пишет автор теста, а не сам сервер. Сервер в `lab/app.py` на создание отвечает `201`, если заявка действительно новая.

## Красный запуск

Ожидание в `assertEqual` временно стоит `200`. Сервис отвечает `201`, числа разные, тест падает.

- URL: https://github.com/anstep817/DevOps-course/actions/runs/46068373634
- Событие: push
- SHA: 77ef0ec
- Существенная строка лога: AssertionError: 201 != 200

Падает именно assertion ожидаемого статуса. Маршрут `/api/requests` в этом эксперименте не ломался. CI всё равно красный: для workflow провал теста и провал продукта выглядят одинаково — ненулевой код шага.

## Зелёный запуск после возврата `201`

- URL: https://github.com/anstep817/DevOps-course/actions/runs/46069031079
- Событие: push
- SHA: d2fe42c

Итоговый файл теста снова ждёт `201`. SHA красного и зелёного run разные, каждый указан рядом со своей ссылкой.

## Проверка понимания

Ошибочное ожидание красит pipeline, потому что CI проверяет не «приложение мне нравится», а «команда тестов вернула ноль». Если тест требует `200`, а сервис честно отдал `201`, ноль не вернётся. Красный статус в этом случае сигналит о расхождении проверки и ответа, и расхождение внесено в тест специально.
