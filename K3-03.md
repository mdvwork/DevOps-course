# K3-03. Тестовый барьер

После `setup-python` в job `test` стоит отдельный шаг:

```yaml
- name: Run application tests
  run: python -m unittest discover -s tests -p test_app.py -v
```

`continue-on-error` нет: ненулевой код unittest красит job.

## Какой контракт проверяется

`test_create_request` отправляет POST `/api/requests` с телом `{"kind":"screen","key":"test-create"}`. Приложение на создание новой заявки отвечает `201`. Тест сравнивает фактический статус с ожидаемым и ещё проверяет, что в списке заявок `total` равен 1. Это контракт «создание возвращает Created и одна запись сохраняется», а не проверка всего сервиса.

## Неуспешный run

В тесте временно ожидаемый статус заменён с `201` на `200`. Приложение по-прежнему отдаёт `201`, поэтому сравнение не сходится.

- Ссылка: https://github.com/desperact1vess/DevOps-course/actions/runs/46081854003
- Событие: push
- SHA: ecbb700
- Строка ошибки из лога: AssertionError: 201 != 200, ожидается упоминание `201 != 200` в `test_create_request`

Причина красного статуса — ложное ожидание в тесте, а не поломка маршрута создания. CI красный, потому что доверяет коду выхода тестов: неверный expected делает assertion ложным, unittest завершается с ошибкой, шаг падает.

## Исправленный run

Ожидание возвращено на `201`. В итоговой версии `tests/test_app.py` снова сравнивает статус с `201`.

- Ссылка: https://github.com/desperact1vess/DevOps-course/actions/runs/46082167106
- Событие: push
- SHA: 6d79d73

Оба SHA относятся к разным коммитам: первый к версии с `200`, второй к версии с `201`.

## Проверка понимания

Неверное ожидание теста делает CI красным, даже когда приложение ведёт себя правильно. Pipeline не знает «истину» отдельно от теста. Красный цвет здесь означает «проверка не сошлась», и этой проверкой было ошибочное `200`.
