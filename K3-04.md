# K3-04. Сборка после тестов

Сборка вынесена из job `test` в свой job. Общий YAML у них только на уровне workflow: машины разные.

- `runs-on: ubuntu-latest` у `build` свой;
- `needs: test` не даёт стартовать сборке, пока тест не зелёный;
- checkout повторяет SHA `d23441a48e516b6c34aea4fa41551a30e30af803`, иначе в каталоге job нет `lab/`;
- команда: `docker build -f lab/Dockerfile -t devops-student:${{ github.sha }} lab`.

Контекст сборки — каталог `lab`. Тег содержит SHA именно этого run. Для pull request GitHub может подставить SHA результата слияния, его и надо смотреть на странице run, а не угадывать по последнему коммиту ветки.

`lab/Dockerfile` должен быть уже сдан на КТ2. Пример в `templates/Dockerfile.example` только перечисляет пункты и сам по себе образ не собирает.

## Неуспешный тест пропускает сборку

После появления job `build` ожидание в `test_create_request` ещё раз меняется с `201` на `200`.

- URL: https://github.com/anstep817/DevOps-course/actions/runs/46071765255
- Событие: push
- SHA: de61bfb

`test` завершается failed. `build` получает статус skipped и шаги не выполняет. Так `needs` отличается от простого порядка шагов внутри одного job: второй job целиком не ставится в работу.

## Оба job зелёные

Тест снова ждёт `201`. В одном run и `test`, и `build` successful.

- URL: https://github.com/anstep817/DevOps-course/actions/runs/46072022039
- Событие: push
- SHA: 551b0e8
- Строка с тегом или командой сборки: docker build -f lab/Dockerfile -t devops-student:d758619d54cd3efb136f63884e7d707cd296d7a lab

## Проверка понимания

Образ остаётся на runner. Когда GitHub уничтожает машину job, тег пропадает. Чтобы образ пережил job, его нужно отправить в registry. Этот workflow push не делает.
