# K3-04. Сборка после тестов

В `Student CI` есть отдельный job `build`:

```yaml
build:
  runs-on: ubuntu-latest
  needs: test
  steps:
    - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      with:
        persist-credentials: false
    - name: Build image
      run: docker build -f lab/Dockerfile -t devops-student:${{ github.sha }} lab
```

`needs: test` ставит `build` в очередь только после успешного `test`. Checkout в `build` обязателен: это другой runner, диска job `test` у него нет. SHA action checkout совпадает с job `test`.

`${{ github.sha }}` — коммит, который обрабатывает данный run. На `pull_request` это может быть SHA пробного слияния, а не SHA головы ветки. Тег образа: `devops-student:` плюс этот SHA.

Для сборки в форке уже должен лежать свой `lab/Dockerfile` с КТ2. Файла `templates/Dockerfile.example` недостаточно: это комментарии с требованиями, Docker его как инструкцию сборки не выполнит.

## Run, где тест красный, а build пропущен

Эксперимент K3-03 повторён уже при существующем job `build`: в `test_create_request` ожидаемый статус снова временно `200`.

- Ссылка: https://github.com/desperact1vess/DevOps-course/actions/runs/46081854003
- Событие: push
- SHA: ecbb700
- Статус job `test`: failed
- Статус job `build`: skipped

Зависимость сработала: GitHub не запускает job, у которого `needs` указывает на неуспешный job. Образ в этом run не собирался, строки `docker build` в логе `build` нет.

## Проверка понимания

После удаления runner образ не останется нигде, если его не отправили в registry. Тег `devops-student:<SHA>` живёт на диске временной машины. Новый job получает новый диск. Без `docker push` в общий registry следующий запуск этот образ не увидит.
