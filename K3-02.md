# K3-02. Первый workflow

Файл: `.github/workflows/student-ci.yml`. Имя workflow в журнале Actions: `Student CI`.

## Свой запуск

- Ссылка на run `Student CI`: https://github.com/desperact1vess/DevOps-course/actions/runs/46080874408
- Событие этого run (`push` или `pull_request`): push
- SHA, который обрабатывает run: aa3d42b
- Runner: `ubuntu-latest`
- Job: `test`

Если Actions в копии выключены и включить их нельзя, здесь пишется фактическая причина, а файл workflow всё равно остаётся в репозитории.

## Что видно в шагах

1. Checkout — шаг `actions/checkout` с SHA `d23441a48e516b6c34aea4fa41551a30e30af803` (v6). Он скачивает в runner именно тот коммит, который проверяет этот run. `persist-credentials: false` не оставляет токен для дальнейших `git push` из job.
2. Setup Python — `actions/setup-python` с SHA `ece7cb06caefa5fff74198d8649806c4678c61a1` (v6), версия `3.13`. Шаг ставит интерпретатор на чистую машину, в репозитории своего Python нет.
3. `python --version` печатает строку версии в лог. Её нужно найти в выводе шага и при необходимости вставить сюда: Python 3.13.18

Job — это набор шагов на одном runner с общим диском. Step — одна команда или один action внутри job. Падение шага красит job и, без `continue-on-error`, не пускает следующие шаги того же job.

Шаблон слушает и `push`, и `pull_request`. В отчёт записывается событие выбранного run, а не оба сразу.

## Проверка понимания

Зелёный `python --version` не подтверждает работу приложения. Команда только спрашивает интерпретатор, какой он версии. Она не читает `lab/app.py`, не открывает порт и не вызывает `/api/requests`. Сервис может быть сломан, а этот шаг всё равно зелёный.
