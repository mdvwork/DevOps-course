# K3-01. CI/CD и ветки

Реальный запуск Actions на этом шаге не требуется.

## Что происходит на каждом участке

Для учебного сервиса заявок (`lab/app.py`) цепочка такая.

1. Событие запуска проверок — `push` или `pull_request` в workflow `Student CI`. Пока коммит только на компьютере, проверка не стартует.
2. Автоматический тест — job `test`: `python -m unittest discover -s tests -p test_app.py -v`. Он поднимает API и web и проверяет контракт HTTP, в том числе создание заявки со статусом `201`.
3. Сборка — отдельный job `build`. Он делает образ `devops-student:<SHA>` из `lab/Dockerfile` только если тест завершился успешно (`needs: test`).
4. Решение о выпуске — ручной шаг после зелёной проверки: слияние короткой ветки в `main` своей копии. Workflow сам в registry ничего не публикует и сервис никуда не выкладывает.

Обратная связь об ошибке появляется на том шаге, который первым завершился ненулевым кодом. Ошибка теста видна в логе `Run application tests`, и `build` при этом пропускается. Ошибка сборки видна уже в `Build image`, когда тесты зелёные.

## Схема веток

```text
короткая ветка kt3
        |
        |  commit
        v
открыть PR в main своей копии
        |
        |  событие pull_request
        v
Student CI: test, затем build
        |
        +-- красный статус: PR не сливать, править ту же ветку
        |
        +-- зелёный статус: человек решает слить PR в main
```

Проверка стоит до слияния. В `main` попадает уже просмотренный коммит, а не каждый черновик.

## Почему не Git-flow

Git-flow держит долгоживущие `develop` и `main`, отдельные `release` и `hotfix`. Для одной учебной работы это лишние ветки: нет нескольких версий в проде и нет параллельных релизов. Короткая ветка и один PR в `main` своей копии дают то же место для автоматической проверки и ревью, без второй постоянной линии разработки.

`main` репозитория преподавателя не используется как цель PR. Сдача — это PR внутри своей копии.

## Проверка понимания

Сборка образа не является автоматическим deployment. `docker build` только создаёт образ на диске runner. Пока образ не отправлен в registry и никто не запустил контейнер на сервере, пользователи сервис не получают. После удаления runner локальный образ исчезает вместе с машиной.
